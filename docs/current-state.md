# Текущее состояние и передача работы

Снимок: 28 октября 2026 года. Изменение авторизации `c97ac13` слито fast-forward в локальную ветку `main`. До слияния рабочее дерево было чистым, `main` отслеживал `origin/main`. Это состояние исходников и локальных проверок, не подтверждение работы production. Перед следующей задачей проверить Git и сервер заново.

## Реализовано в исходниках

- Новый пользователь входит через Telegram OpenID Connect и получает статус `PENDING`. До одобрения администратора ему доступна только страница ожидания. `ACTIVE` получает доступ, `BLOCKED` не может войти снова и теряет доступ по действующей cookie.
- Администратор видит подтверждённый Telegram-профиль в `/settings` и может одобрить, удалить ожидающую заявку, заблокировать или вернуть аккаунт в заявки. Старые парольные аккаунты продолжают работать и могут привязать Telegram к своему профилю.
- Обычная регистрация по инвайту закрыта; сохранён первичный bootstrap администратора по мастер-ключу. Исторические `InviteCode` в БД не удалялись.
- Добавлены OIDC-маршруты, серверная проверка ID-токена, миграция статуса и Telegram-полей `User`, новая зависимость `openid-client`, настройки web и соответствующие тесты. Обновлены README, API, схема БД, эксплуатационная инструкция, архитектура и карта проекта.

## Ограничения и следующий шаг

Реальный Telegram callback и сценарий одобрения в браузере не проверялись: BotFather зарегистрирован для `https://tgmons.online`, а локальный адрес `http://localhost:4000` намеренно не начинает OIDC-вход с production callback. Секрет прочитан из локального `C:\\tgid.md` и записан только в игнорируемый Git локальный `.env`; production окружение не менялось. На сервере перед включением входа понадобятся те же три переменные Telegram Login и `prisma migrate deploy`. Запуск production требует отдельной команды.

Следующий шаг: после разрешённого развёртывания на зарегистрированном HTTPS-домене пройти вход тестового Telegram-аккаунта, одобрение, блокировку действующей сессии и привязку прежнего аккаунта.
