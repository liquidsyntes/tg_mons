# ADR 0001: Архитектура модуля антифрода и агрегированного скоринга накруток (Anti-Fraud Detection Architecture)

## Статус (Status)
**Принято и реализовано (Accepted & Implemented)** — 2026-09-13

---

## Контекст (Context)
Экосистема каналов в Telegram активно используется для коммерческого маркетинга и размещения рекламы. В связи с этим индустрия сталкивается с систематическими попытками искусственного завышения ключевых метрик:
1. **Накрутка балластной аудитории:** систематическое добавление ботов в состав подписчиков для создания иллюзии крупного медиаканала.
2. **Накрутка просмотров:** использование сервисов автопросмотров для завышения охвата одного поста и продажи рекламы по завышенным CPM.
3. **Шаблонные реакции:** закупка пакетов реакций бот-фермами с фиксированной пропорцией относительно просмотров публикации.
4. **Рост через серые каталоги без открытого цитирования:** резкое увеличение числа подписчиков без органических пересылок и рекомендаций в других открытых каналах Telegram.

### Проблематика существующих решений
Традиционные одиночные эвристики (например, проверка только соотношения просмотров к числу подписчиков `views / members`):
- Дают неприемлемо высокий процент ложноположительных срабатываний (False Positives) для специализированных, нишевых или авторских каналов с редкими публикациями.
- Не способны детектировать комбинированные схемы накруток, когда одновременно накручиваются и подписчики, и просмотры.
- Не обеспечивают рекламодателю прозрачного и понятного объяснения (Explainability), почему канал классифицирован как рискованный.

Возникла потребность в создании многофакторной, детерминированной, масштабируемой и полностью прозрачной архитектуры антифрода в рамках проекта TgMon.

---

## Решение (Decision)

Мы спроектировали и внедрили гибридную двухуровневую архитектуру (Two-Tier Architecture), объединяющую:
1. **Детерминированный набор специализированных эвристических детекторов** (`src/lib/fraudDetector.ts`, `src/lib/citationIndex.ts`).
2. **Двухуровневое разделение ответственности (Two-Tier Execution):** фоновый сборщик (Worker) для обнаружения и персистентности сигналов в базе данных + легковесная динамическая агрегация (Web Query Layer) для мгновенного расчета единого скора риска `fraudScore`.
3. **Единую прозрачную аддитивную модель скоринга (0–100%)** и компонент визуализации `RiskBadge`.

### Архитектурный дизайн (Architectural Design)

```
       [ Telegram MTProto API ]
                  │
                  ▼
   [ Worker: src/worker/collector.ts ]
   ├── Сбор истории постов и снапшотов
   ├── Запуск фоновых эвристик:
   │   ├── checkGrowthSmoothness(metrics)
   │   ├── checkUncorrelatedSpikes(metrics, posts, mentions)
   │   ├── checkViewsToSubsRatio(posts, members)
   │   └── checkUniformReactionRatio(posts)
   └── Сохранение аномалий (try-catch изоляция)
                  │
                  ▼
    [ PostgreSQL: fraud_signals ]
                  │
                  │ (чтение истории аномалий)
                  ▼
 [ Web Query Layer: src/lib/metrics/queries.ts ]
   ├── getCitationIndicesForChannels()
   └── runFraudAudit(channel)  <── Динамическое объединение
                  │
                  ▼
 [ Next.js UI Presentation ]
   ├── RiskBadge: "Risk of Artificial Traffic: X%"
   └── MyChannelCard: "Индекс цит. (30д)" + AlertTriangle
```

#### 1. Уровень хранения и фонового анализа (Worker Tier)
В цикле сбора данных воркера (`src/worker/collector.ts`):
- Загружается 30-дневная история ежедневных метрик и постов канала.
- Независимо запускаются эвристические проверки:
  - `checkGrowthSmoothness` — анализ коэффициента вариации приростов подписчиков.
  - `checkUncorrelatedSpikes` — сопоставление скачков подписчиков с датами публикаций и внешних упоминаний.
  - `checkViewsToSubsRatio` — выявление дисбаланса охватов и аудитории.
  - `checkUniformReactionRatio` — вычисление дисперсии вовлеченности (ERR) последних публикаций.
- При срабатывании любой проверки сформированный сигнал сохраняется в таблицу `fraud_signals` (Prisma-модель `FraudSignal`).
- **Изоляция отказов:** выполнение проверок антифрода обёрнуто в блок `try/catch`. Сбой или исключение в детекторе логируется, но **никогда не прерывает** основной цикл сбора и материализации метрик.

#### 2. Уровень динамической агрегации (Web Query Tier)
В слое веб-запросов (`src/lib/metrics/queries.ts`):
- При отображении списка каналов или страницы канала вызывается функция `runFraudAudit(channel)`.
- Функция анализирует свежие посты и снапшоты, а также учитывает персистентные сигналы из таблицы `fraud_signals`, гарантируя актуальность данных даже при задержках материализации.
- Рассчитывается единый скор риска `fraudScore` от 0 до 100%.

#### 3. Модель скоринга и визуализация риска (`RiskBadge`)
Итоговый показатель риска вычисляется по дискретной аддитивной формуле:
$$\text{fraudScore} = \sum_{j=1}^{4} \Big(\text{flag}_j \times 25\Big) \in \{0, 25, 50, 75, 100\}$$
где $\text{flag}_j$ соответствует четырём базовым детекторам:
1. `viewsToSubsRatio` (Аномальное соотношение просмотров к подписчикам).
2. `growthSmoothness` (Аномальная гладкость роста).
3. `uncorrelatedSpikes` (Нескоррелированные скачки подписчиков).
4. `uniformReactionRatio` (Равномерность реакций ERR).

Градации визуализации в `src/components/RiskBadge.tsx`:
- **0% (Clean / Emerald):** `bg-emerald-500/15 text-emerald-400 border-emerald-500/30`, иконка `ShieldCheck`. Все детекторы чисты (подсказка: «Низкий риск накрутки»).
- **25% (Low / Amber):** `bg-amber-500/15 text-amber-400 border-amber-500/30`, иконка `AlertTriangle`. Обнаружена одна изолированная аномалия.
- **50% (Moderate / Rose):** `bg-rose-500/15 text-rose-400 border-rose-500/30`, иконка `AlertTriangle`. Две одновременных аномалии.
- **75% (High / Rose):** `bg-rose-500/15 text-rose-400 border-rose-500/30`, иконка `AlertTriangle`. Три одновременных аномалии.
- **100% (Critical / Rose):** `bg-rose-500/15 text-rose-400 border-rose-500/30`, иконка `AlertTriangle`. Все четыре фактора сработали.
- Всплывающая подсказка (Tooltip) формирует структурированный список причин срабатывания с точными текстовыми формулировками детектора.

#### 4. Индекс цитирования и кросс-проверка (`calculateCitationIndex` & `checkLowCitationGrowth`)
Для оценки внешнего авторитета канала внедрен логарифмический индекс цитирования:
$$\text{CI} = \sum_{i=1}^{M} \Big(\text{count}_i \times \log_{10}(\text{subscribers}_i)\Big)$$
- Учитывает упоминания за последние 30 дней.
- Исключает самоцитирования (`sourceChannelId === targetId`).
- Отсекает каналы с числом подписчиков $\le 1$ (вес 0), исключая логарифмические сингулярности.
- Проверка `checkLowCitationGrowth` маркирует каналы, у которых темп роста за 30 дней $G_{30\text{d}} > 5\%$ при $\text{CI} \le 1.0$.

## Обоснование эмпирических порогов (Empirical Thresholds & Justifications)

| Параметр | Значение порога | Обоснование и физический смысл |
|---|---|---|
| **Минимальная история метрик ($N$)** | $\ge 14$ дней | На коротких отрезках (менее двух недель) случайные колебания органического трафика могут симулировать ложную линейность. 14 дней — достаточный статистический базис. |
| **Коэффициент вариации роста ($CV$)** | $CV < 0.1$ ($< 10\%$) | В естественной среде недельная цикличность (выходные vs будни), отписки и всплески от публикаций дают $CV \ge 0.20-0.60$. Относительное отклонение $< 10\%$ математически недостижимо без скрипта с суточным лимитом подписок. |
| **Отношение просмотров к подписчикам** | $< 0.05$ и $> 1.50$ | Нормальный диапазон охвата публикации в Telegram составляет $10\%-50\%$. Охват $< 5\%$ свидетельствует о наплыве ботов, а $> 150\%$ без виральных репостов — о систематической закупке автопросмотров. |
| **Минимум постов для ratio ($K$)** | $\ge 5$ постов | Предотвращает ложные выводы на каналах с 1–2 нетипичными постами. |
| **Динамический порог скачка ($T$)** | $\max(3\mu_\Delta, 50, 0.005 F_{\max})$ | $3\mu_\Delta$ отсекает локальный шум; константа $50$ защищает начинающие каналы от срабатываний на естественные единичные подписки; $0.005 F_{\max}$ (0.5%) защищает каналы-миллионники от флуктуаций в сотни подписчиков. |
| **Окно корреляции скачка** | $[D-1, D]$ (2 дня) | Учитывает задержки прочтения рекламных интеграций пользователями и возможную разницу временных зон серверов Telegram. |
| **Порог быстрого роста ($G_{30\text{d}}$)** | $> 5\%$ за 30 дней | Стандартный порог активного масштабирования устоявшегося канала. |
| **Порог околонулевого цитирования ($\text{CI}$)** | $\text{CI} \le 1.0$ | При $\text{CI} \le 1.0$ канал имеет менее одного упоминания от микроканала на 10 подписчиков ($\log_{10}(10) = 1$). Рост без внешнего следа свидетельствует о покупке трафика в каталогах накруток. |
| **Минимум постов для ERR ($N$)** | $\ge 10$ постов | Минимальный объем выборки, необходимый для надежного расчета дисперсии вовлеченности. |
| **Коэффициент вариации реакций ($CV_{\text{ERR}}$)** | $CV_{\text{ERR}} < 0.1$ | Живая аудитория реагирует на контент избирательно в зависимости от тематики. Разброс ERR реальных каналов составляет $20\%-60\%$. Однородность $CV < 0.1$ указывает на накрутку фиксированного пакета реакций на каждый пост. |

## Рассмотренные альтернативы (Alternatives Considered)

### 1. Модели машинного обучения (Machine Learning / Classification Trees)
- **Суть альтернативы:** Обучение supervised-классификатора (CatBoost, LightGBM, Random Forest) на размеченном датасете каналов.
- **Причина отклонения:**
  - Отсутствие открытого, объективно валидированного и постоянно обновляемого эталонного датасета «накрученных» каналов Telegram.
  - Проблема «черного ящика»: маркетологи и покупатели рекламы требуют прозрачных объяснений («почему этот канал подозрителен?»), а не абстрактной вероятности 0.87.
  - Избыточная сложность эксплуатации: необходимость инференса Python/ONNX в production-окружении Next.js/Node.js, риск деградации модели (model drift) со временем.
- **Выбор:** Детерминированные математические эвристики с прозрачным объяснением каждого обнаруженного фактора.

### 2. Синхронное сохранение сигналов при открытии страниц (On-demand Persistence)
- **Суть альтернативы:** Запуск всех расчетов и запись в базу данных непосредственно в Next.js Route Handlers / Server Components.
- **Причина отклонения:**
  - Создает избыточную нагрузку на запись в PostgreSQL при чтении популярных страниц каталога.
  - Риск race conditions и деградации времени отклика интерфейса (TTFB).
- **Выбор:** Разделение на асинхронный воркер (фоновый анализ и запись в БД) и легковесный динамический аудит при чтении.

### 3. Нелинейная система штрафов (Сигмоидальные / Логистические веса)
- **Суть альтернативы:** Назначение непрерывного скора риска с неравными весами признаков.
- **Причина отклонения:**
  - Нелинейные шкалы трудны для интуитивного восприятия конечными пользователями.
- **Выбор:** Равновесная 4-факторная аддитивная шкала (по 25% за каждый сработавший домен проверки), формирующая четкие дискретные уровни риска: 0%, 25%, 50%, 75%, 100%.

## Компромиссы (Trade-offs)

1. **Консервативность vs Чувствительность (False Positives vs False Negatives):**
   - Мы намеренно выбрали консервативные пороги ($N \ge 14$ дней, $K \ge 10$ постов, 2-дневное окно корреляции). Это минимизирует ложные обвинения в накрутке честных молодых каналов, однако допускает задержку обнаружения на начальных стадиях накрутки до накопления минимальной выборки.
2. **Ограничение контура цитирования:**
   - Индекс $\text{CI}$ фиксирует только упоминания внутри платформы Telegram. Если канал масштабируется через внешние рекламные каналы (YouTube-интеграции, таргетированная реклама Telegram Ads, закупка в Яндекс.Директ), его органический Telegram $\text{CI}$ может оставаться невысоким. Именно поэтому сигнал `checkLowCitationGrowth` не включен в автоматический штраф `fraudScore`, а вынесен в карточку канала как контекстная метрика для экспертной оценки аналитиком.

## Последствия (Consequences)

### Положительные последствия
- **Автоматизация контроля качества трафика:** Платформа автоматически сегментирует каналы по уровню риска без необходимости ручной модерации.
- **Высокая производительность:** Расчет `runFraudAudit` выполняется за $< 2$ мс в рамках рендеринга страницы, не блокируя серверный пайплайн.
- **Отказоустойчивость:** Любые сбои в анализе антифрода в воркере изолированы и не нарушают цикл сбора ключевых метрик каналов.
- **Полная прозрачность для пользователей:** Компонент `RiskBadge` предоставляет исчерпывающую расшифровку причин во всплывающей подсказке.

### Ограничения и эксплуатационные требования
- Каналы с числом публикаций менее 10 или историей мониторинга менее 14 дней имеют статус недостаточных данных до накопления требуемой статистики.
- Для расчета `checkUncorrelatedSpikes` требуется наличие актуальных данных по входящим упоминаниям (`mentionsDates`).
