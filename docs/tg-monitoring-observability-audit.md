# Аудит наблюдаемости (Observability) Backend-части TgMon

Данный документ содержит результаты аудита серверной части проекта TgMon с фокусом на логирование, мониторинг, обработку ошибок и статус фоновых задач.

## 1. Карта потока данных

1. **Запуск задачи (Cron):** 
   - `node-cron` в `src/worker/index.ts` инициирует функцию `runCollectCycle()` каждый час (или по значению переменной `COLLECT_CRON`).
2. **Получение Telegram-данных:** 
   - Функция в `src/worker/collector.ts` последовательно проходит по всем каналам (`isActive: true`).
   - Используется библиотека `telegram` (GramJS). Через клиент вызываются MTProto-методы: `GetFullChannel` (для количества участников) и `getMessages` (для получения ленты постов и просмотров/реакций).
3. **Расчеты метрик и аналитики:**
   - **Метрики:** Считаются "на лету" (in-memory) при запросе к API. Логика находится в `src/lib/metrics.ts` (`calculateChannelMetricsFromData`). Отдельного фонового процесса для пересчета метрик нет.
   - **Аналитика (AI):** Выполняется по запросу пользователя через API (`src/app/api/ai/summary/route.ts` и др.), где формируется промпт и делается вызов к OpenRouter.
4. **Сохранение в БД:**
   - После получения данных от Telegram, воркер сохраняет результаты в PostgreSQL через Prisma (`prisma.channel.update`, `prisma.snapshot.create`, `prisma.post.upsert`).
5. **API / Интерфейс:**
   - Клиент (Next.js) запрашивает данные через эндпоинты в `src/app/api/...`, которые читают агрегированные данные из базы и возвращают их на клиент.

## 2. Что уже существует для логов, ошибок и статусов

- **Логирование событий:** 
  - Реализовано через стандартные `console.log` и `console.error` в `src/worker/index.ts` и `src/worker/collector.ts`. В консоль выводятся старты циклов, успехи по каналам, время выполнения в миллисекундах и ошибки.
- **Обработка Rate Limits (Telegram):**
  - Присутствует хорошая обертка `withRateLimitAndRetry` (`src/worker/collector.ts:31`), которая перехватывает ошибки `FLOOD_WAIT`, извлекает время блокировки и ставит процесс на паузу, делая до 3 попыток.
- **Статусы мониторинга в БД:**
  - В `prisma/schema.prisma` у модели `Channel` есть поля:
    - `isActive` — флаг мониторинга.
    - `lastCollectedAt` — время последнего успешного сбора (обновляется в конце успешного цикла `src/worker/collector.ts:378`).
    - `lastError` — строковое поле, куда записывается сообщение последней ошибки (очищается при успехе).
- **Оповещения (Alerts):**
  - Встроена функция `sendTelegramAlert` (`src/worker/collector.ts:7`), которая отправляет уведомление в Telegram-чат админа при аномальных отписках/подписках (более 1% или 500 человек за цикл).

## 3. Чего нет или недостаточно для быстрого поиска проблем

1. **Нет истории выполнения задач (Job History):** В базе нет информации о том, сколько длились прошлые циклы, падал ли воркер полностью ночью, сколько каналов успешно обновилось вчера.
2. **Отсутствие структурированного логирования:** Использование обычного текста в `console.log` не позволяет легко фильтровать логи (например, найти все записи, где `durationMs > 5000` или `errorType == 'AuthError'`).
3. **Отсутствие таймаутов на сетевые вызовы:** Если вызов MTProto зависнет, весь цикл синхронизации для всех остальных каналов остановится, так как каналы обрабатываются последовательно (`for...of` в `runCollectCycle`), а таймаут на уровне `Promise` не установлен.
4. **Затирание ошибок:** Поле `lastError` хранит только самую свежую ошибку. Если канал упал 10 раз по 10 разным причинам, история падений теряется.
5. **Слепая зона API:** Ошибки генерации AI-отчетов и API-вызовов логируются в консоль, но не сохраняются в БД. Пользователь может столкнуться с 500-й ошибкой, и об этом можно будет узнать только при прямом чтении логов сервера.

## 4. Минимальный рекомендуемый первый этап (Без внешних сервисов)

Создать простую In-House систему Observability:
1. **JSON-Логгер:** Написать простую утилиту `logger.ts`, которая будет выводить логи в формате JSON в stdout. PM2 (или Docker) будет собирать их, а мы сможем легко их читать/парсить.
2. **Таблица SyncJob:** Добавить в Prisma модель для хранения истории запусков воркера (начало, конец, статус, количество успехов и ошибок).
3. **Healthcheck Endpoint:** Сделать маршрут `/api/health`, который проверяет отставание `lastCollectedAt` у последнего `SyncJob`. Если цикл не запускался больше 2 часов — отдавать статус 503. Это позволит подключить простейший внешний Uptime-монитор.

## 5. Предложение единого формата событий

Для перевода логов в машиночитаемый формат рекомендуется использовать следующий JSON-контракт:

```json
{
  "timestamp": "2026-08-26T12:00:00.000Z",
  "level": "info",
  "event": "channel_scan_completed",
  "context": {
    "channel_id": 123,
    "channel_username": "durov",
    "duration_ms": 1450,
    "posts_added": 12,
    "snapshots_added": 1,
    "attempt_number": 1
  },
  "error": null
}
```

## 6. Какие поля статуса полезно хранить для канала/задачи

**Для модели `Channel` (дополнить):**
- `syncStatus`: enum (`IDLE`, `SYNCING`, `ERROR`) — позволяет UI показывать, что данные прямо сейчас обновляются.
- `consecutiveErrors`: Int (по умолчанию 0) — счетчик подряд идущих ошибок. Если достигает 10, можно автоматически переводить канал в `isActive: false`, чтобы не тратить лимиты Telegram.

**Для новой модели `SyncJob` (Таблица задач):**
- `id`: UUID / Int
- `startedAt`: DateTime
- `endedAt`: DateTime?
- `status`: enum (`RUNNING`, `COMPLETED`, `FAILED`)
- `channelsProcessed`: Int
- `errorsCount`: Int

## 7. План внедрения небольшими безопасными шагами

- **Шаг 1:** Внедрить утилиту `logger.ts` и заменить все `console.log` в `worker/` на вызовы логгера. Это не затронет логику сбора.
- **Шаг 2:** Создать Prisma-миграцию с добавлением модели `SyncJob`. Обновить `src/worker/index.ts`, чтобы он создавал запись при старте крона и обновлял при завершении.
- **Шаг 3:** Добавить `consecutiveErrors` в модель `Channel` и инкрементировать его в блоке `catch` функции `runCollectCycle`. При успехе — сбрасывать в 0.
- **Шаг 4:** Обернуть вызовы к MTProto в функцию с `Promise.race` (Таймаут), чтобы один зависший канал не убивал весь цикл на часы.
- **Шаг 5:** Разработать `/api/health` для вывода состояния системы.

## 8. Риски утечки чувствительных данных в логах

1. **Telegram Session (String):** Крайне важно следить за тем, чтобы содержимое переменной `process.env.TG_SESSION` не попало в `console.error` при ошибках инициализации `TelegramClient`.
2. **API Ключи (OpenRouter):** Ошибки от OpenRouter могут содержать полный URL и заголовки запроса в объекте `err`. Логирование сырого объекта `err` (через `console.error(err)`) в API роутах может слить ключ в stdout. Нужно логировать только `err.message`.
3. **Персональные данные:** Логирование текста сообщений или объектов `user` при ошибках парсинга (GramJS) может привести к сохранению в логах номеров телефонов или переписок из чатов, к которым подключен аккаунт. Следует избегать логирования сырых объектов `entity` или `message`.

## 🏆 ТОП-5 самых приоритетных улучшений

1. **Таймауты для MTProto-запросов:** Изолировать каждый вызов к Telegram таймаутом (например, 30 секунд), иначе один "подвисший" ответ от серверов ТГ полностью блокирует сборку всех остальных каналов.
2. **Счетчик 연속ных ошибок (`consecutiveErrors`):** Автоматически отключать `isActive` для каналов (например, удаленных или забаненных), чтобы они бесконечно не триггерили таймауты и ошибки каждый час.
3. **История циклов (`SyncJob`):** Минимальная таблица в БД для отслеживания жизнеспособности воркера, чтобы администратор видел, когда цикл последний раз успешно завершился.
4. **Санитаризация логов:** Строго логировать только `err.message`, чтобы случайно не вывести дамп всего объекта ошибки, который может содержать Session String или Bearer токены.
5. **Healthcheck Endpoint (`/api/health`):** Позволит прикрутить любой бесплатный сервис (UptimeRobot) для уведомлений о падении бэкенда/воркера, закрывая главную слепую зону мониторинга.
