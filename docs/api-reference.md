# Справочник API

Сверено с `src/app/api/**/route.ts` 26 октября 2026 года. Базовый URL локального web: `http://localhost:4000`. `:id` обозначает внутренний ID PostgreSQL, а не Telegram ID. Типы сводных ответов: [src/lib/types.ts](../src/lib/types.ts).

## Формат и доступ

`GET /api/channels/:id/export?dataset=daily|snapshots|posts&format=csv|json` выгружает дневные агрегаты канала, последние 10 000 снимков аудитории или 100 последних постов. `daily` включает всю сохранённую историю `ChannelMetricDaily`; пустая таблица выдаёт CSV с заголовками или JSON `[]`. CSV использует UTF-8 BOM и CRLF. Маршрут требует UI-сессию или Bearer и проверяет, что обычный пользователь подписан на канал. Некорректные параметры дают 400, недоступный канал 404.


Большинство обработчиков возвращает JSON, даты сериализуются как ISO-строки, Telegram BigInt как строки. Экспорт отчётов возвращает HTML, отдельный маршрут изображения возвращает сохранённые байты; некоторые ошибки экспорта имеют plain text. Большинство ошибок имеет `{ "error": "..." }`; health использует `{ "status": "error", "message": "..." }`. Валидация неодинакова: часть ID разбирается через `parseInt`, строгая проверка положительного целого числа есть у демографии, скрытия событий, изображений постов и удаления отчётов.

Все страницы и API, кроме входа и health, проходят общий гард в middleware. Браузер использует подписанную HttpOnly-cookie, межсервисные запросы используют `Authorization: Bearer <COLLECT_API_TOKEN>`. Указание «Гард в обработчике» ниже означает дополнительную проверку внутри маршрута. Отсутствующий серверный ключ даёт 500, отсутствие авторизации даёт 401, неверный Bearer или неподходящий `Origin` для cookie-мутации дают 403.

Middleware больше не добавляет Bearer к запросам браузера. Если клиент передал неверный заголовок `Authorization`, действующая cookie не подменяет его. Cookie действует 12 часов и привязана к текущему `COLLECT_API_TOKEN` через HMAC; смена ключа делает старые cookie недействительными. `SameSite=Strict` и проверка точного `Origin` защищают изменения по cookie от межсайтового запроса. В приложении есть роли `ADMIN` и `USER`, но нет серверного списка сессий: выход очищает cookie браузера, а выданная ранее копия действует до истечения срока или смены ключа. Для внешнего доступа необходим HTTPS. `/api/internal/*` принимает только Bearer.

### Вход, регистрация и инвайты

- `GET /login`: форма входа по логину/паролю, регистрации по инвайт-коду (включая `?invite=...`) и резервного входа по мастер-ключу.
- `POST /api/auth/login`: принимает `{username, password}` либо `{accessKey}` и `Origin` текущего сайта. При успешной проверке устанавливает подписанную HttpOnly-cookie на 12 часов (`v2.<userId>.<role>...` для пользовательских аккаунтов). Для первого `ADMIN`-аккаунта автоматически привязывает ранее собранные каналы, отчёты и правила алертов.
- `POST /api/auth/register`: принимает `{username, password, inviteCode}` и `Origin` текущего сайта. Если в БД ещё нет администраторов (`ADMIN`), в качестве `inviteCode` принимается серверный `COLLECT_API_TOKEN` (создаёт первого `ADMIN` и привязывает к нему текущие каналы). Для остальных пользователей проверяет и погашает одноразовый код из `InviteCode` и создаёт пользователя с ролью `USER`.
- `GET /api/auth/me`: возвращает `{ user: { id, username, role } }` для текущей сессии.
- `GET /api/invites`, `POST /api/invites`, `DELETE /api/invites`: управление одноразовыми инвайт-кодами и просмотр списка зарегистрированных пользователей (доступно только роли `ADMIN`).
- `POST /api/auth/logout`: очищает cookie и перенаправляет на `/login` со статусом 303. Требует действующей сессии или Bearer; для cookie нужен совпадающий `Origin`.
- `GET /api/health` остаётся открытым для проверки состояния сервиса. Все остальные GET API требуют сессию или Bearer; изменения также проходят гард в соответствующем обработчике.
- `GET /api/version` возвращает `{ "version": "abc1234" }` с коротким SHA запущенной версии или `{ "version": null }`, если метаданные коммита недоступны. Ответ не кэшируется и требует сессию или Bearer.

## Каналы

| Метод и путь | Вход | Ответ / поведение | Гард в обработчике |
| --- | --- | --- | --- |
| `GET /api/channels` | — | Массив `ChannelMetrics` из overview, включая отключённые каналы | Нет |
| `POST /api/channels` | `{ "input": "@example_channel", "isMine": false }` | 201, метрики добавленного/повторно активированного канала; worker выполняет resolve и попытку backfill до ответа; при недоступном worker 503 | Да |
| `GET /api/channels/:id` | ID | `ChannelMetrics`; 400 для нечислового ID, 404 если канала нет | Нет |
| `PATCH /api/channels/:id` | Необязательные boolean `isActive`, `isMine` | Обновлённые метрики; назначение `isMine: true` снимает прежний флаг в транзакции | Да |
| `DELETE /api/channels/:id` | Необязательное `?permanent=true` | По умолчанию `isActive=false`, ответ `{success,message,channel}`; permanent удаляет запись с каскадами и возвращает `{success,message}` | Да |
| `PUT /api/channels/:id/favorite` | `{ "isFavorite": true }` | `{ "success": true, "isFavorite": true }`; кэши метрик не сбрасывает | Да |
| `GET /api/channels/:id/ltv` | ID | `{ "ltv": [{ "hour": 1, "percent": 12.3 }, ...] }` либо `{ "ltv": [] }` | Нет |
| `GET /api/channels/:id/network` | ID | Совместимый плоский ответ `{ "outbound": [...], "inbound": [...] }`, ограниченный доступными каналами пользователя | Да |
| `GET /api/channels/:id/ad-price` | ID | `{estimatedPricePerPost,cpm,confidence,averageAdReach,averageReachCurve,priceSource,customAdPriceUah,customCpmUah,canEdit}`; 404 если канал недоступен | Да |
| `PATCH /api/channels/:id/ad-price` | `{customAdPriceUah?,customCpmUah?}` | `{success,customAdPriceUah,customCpmUah,priceSource}`; 400 при неверных значениях, 403 для мастер-сессии, 404 при отсутствии личной подписки | Да |
| `GET /api/channels/:id/ad-attribution` | ID, `days=7|30|90` (по умолчанию 30) | `{periodDays,inbound,outbound}` с приростом подписчиков +24/+48 ч и оценочными ценой/CPF | Да |

`input` принимает username, Telegram-ссылку или invite-ссылку уже доступного аккаунту чата. Неверный/пустой input даёт 400. Неудачный backfill сохраняет `lastError`, но не обязательно отменяет 201. Добавление, PATCH и DELETE очищают `metricsCache`/`bestTimeCache`.

`GET /api/channels/:id` использует `calculateChannelMetrics`, который не добавляет все поля overview (например, EP/консолидированный антифрод); для полной детализации используйте `/api/stats/channel/:id`.

`GET /api/stats/citation-network?channelId=123&days=30` возвращает `{focalChannelId,days,nodes,edges,discoveredHubs,propagation}`. `channelId` обязателен и должен входить в активные `UserChannel` пользователя; мастер-сессия без `userId` использует все активные каналы. `days` принимает 7, 30 или 90 (по умолчанию 30); неверные параметры дают 400, недоступный канал 404. Рёбра считают упоминания и пересылки по `Post.publishedAt`, исключают самоцитирования и отмечают встречное направление. Внешние узлы содержат только видимый в посте username, без метрик каналов из чужих списков. `discoveredHubs` использует фиксированные последние 30 дней и минимум два уникальных канала-источника. В граф включаются до 30 наиболее часто упоминаемых внешних username; пересылки с одним лишь Telegram ID не становятся рекомендацией. `propagation` содержит роль канала, `originRatio`, входящие и исходящие счётчики, среднюю подтверждённую задержку, топ цитируемых постов и последние цепочки. Эта часть всегда использует окно 30 дней и только каналы текущего пользователя; неизвестная задержка возвращается как `null`.

LTV строится по PostSnapshot для постов за 14 дней с ≥2 снимками и ранним замером до округлённого шестого часа; результат охватывает часы 1–72. Пустой LTV не означает отсутствие канала: отдельной проверки его существования нет. Network агрегирует сохранённые исходящие/входящие упоминания, а не обращается к Telegram за новым графом.

Новые PostSnapshot записываются только в первые 72 часа после публикации с интервалом от 45 минут. Записи старше 30 дней удаляются worker после основного цикла.

У ad-price отсутствие рекламы или пригодных просмотров возвращает 200 с `averageAdReach: null` и пустой кривой. `estimatedPricePerPost` при этом равен личной фиксированной цене, если она положительна, иначе `null`. Приоритет: `customAdPriceUah > 0`, затем `customCpmUah > 0`, затем нишевый CPM. `priceSource` принимает `custom_price`, `custom_cpm` или `niche_estimate`. PATCH принимает только целые неотрицательные значения до 2147483647 или `null` для сброса; пустое тело и неизвестные поля дают 400. `confidence` равен `high` при ≥3 рекламных постах, иначе `low`; это правило по числу постов, не статистический доверительный интервал. Все суммы и CPM указаны в гривнах.

## Статистика

| Метод и путь | Параметры | Ответ |
| --- | --- | --- |
| `GET /api/stats/overview` | — | `{myChannel,channels,totalChannels,activeChannels,lastGlobalUpdate}` |
| `GET /api/stats/dashboard` | Нет тела | KPI, `avgErr`, `avgScore`, topGainers/topLosers, postsTimeline/subscribersTimeline только по активным каналам |
| `GET /api/stats/channel/:id` | `period=24h`, `7d` или `30d`, default `7d` | `{channel,myChannel,period,scoreBreakdown,membersHistory,postsDistribution,vrHistory,heatmapData,myHeatmapData,recentPosts,popularReactions,contentTypePerformance,silencePeriods}` |
| `GET /api/stats/compare` | Обязательные `a`, `b` — ID каналов; `period` как выше | `{ "a": ChannelDetailStats, "b": ChannelDetailStats, "period": "7d" }`; 400 без ID, 404 если канал не найден |
| `GET /api/stats/best-time` | Нет параметров | `{timeZone,bestDay,bestHour,score,avgViews,avgVr,postCount,heatmap}` или `null`, если нет активных конкурентов |
| `GET /api/stats/trends` | — | Последний сохранённый trend: `{createdAt,data}`; `null` при отсутствии/невалидном JSON, новую генерацию не запускает |
| `GET /api/stats/demographics/:id` | Положительный Int ID | Последний языковой снимок; контракт ниже |

Эти GET доступны с Web UI-сессией или Bearer; отдельного гарда в обработчиках нет. Overview/dashboard/detail кэшируются в web на 5 минут, best-time на 30 минут. Detail берёт EP из кэшированного overview; при пустом кэше overview рассчитывается и сохраняется для следующих запросов. Неизвестное значение period заменяется на `7d`. Best-time использует VR и количество постов; `avgVr` уже в процентах. Дни/часы слотов берутся в часовом поясе процесса.

### Демография

```json
{
  "demographics": {
    "capturedAt": "2026-09-16T00:00:00.000Z",
    "languages": [{ "code": "en", "name": "English", "percent": 100 }],
    "countries": null,
    "geographyStatus": "unsupported",
    "notificationsEnabledPercent": 24.5
  }
}
```

- Некорректный ID: 400; отсутствующий канал: 404.
- Нет снимка: 200 и `{ "demographics": null }`. Причина отсутствия из этого ответа не определяется.
- Повреждённые доли или ошибка БД: 500 с безопасным сообщением.
- `languages` отсортированы по убыванию доли. Страны не определяются по языкам; `countries: null` не означает нулевую аудиторию.
- `notificationsEnabledPercent` содержит процент подписчиков канала с включёнными уведомлениями (`0..100`, float с одним знаком после запятой) или `null`, если значение не получено из Telegram API.
- API читает БД; MTProto-сбор запускается отдельным cron worker.

## Поиск постов

`GET /api/posts/search`: GET с query-параметрами, доступен после входа или с Bearer.

| Параметр | Значение |
| --- | --- |
| `channelId` | Необязательный положительный ID; без него выполняется глобальный поиск |
| `q` | Подстрока текста, поиск без учёта регистра |
| `dateFrom`, `dateTo` | Границы публикации; dateTo расширяется до конца дня в часовом поясе процесса |
| `minViews`, `maxViews` | Границы просмотров |
| `type` | `all` по умолчанию; `ads` выбирает сохранённые `Post.isAd: true`, `partners` использует текстовые маркеры |
| `limit`, `offset` | Пагинация; `limit` от 1 до 50, `offset` от 0 до 100000 |
| `sortBy` | Старые значения: `date`, `views_desc`, `views_asc`; глобальный поиск: `publishedAt`, `views`, `er`, `err`, `forwards` |
| `onlyAds` | `true` выбирает сохранённые рекламные посты; `false` оставляет все посты |
| `advertiser` | Необязательный `@username` рекламируемой цели; выбирает только рекламные посты с соответствующим `Mention` |
| `onlyViral` | `true` оставляет только вирусные посты по 30-дневной базовой линии канала; сочетается с остальными фильтрами |
| `niche` | Ниша из `UserChannel` для обычной сессии или из `Channel` для мастер-сессии |
| `days` | `7`, `14`, `30` или `90`; по умолчанию 30 в глобальном поиске |

`posts[].text` — обычный текст или `null`. Для успешно собранной статьи это текст, извлечённый из `richMessage`, а не HTML и не набор блоков Telegram. Нового поля или отдельного endpoint статей нет. При неудачной догрузке сохраняется прежний текст, если он был; причина отсутствия текста отдельным полем не возвращается.

Ответ: `{posts,total,absoluteTotal}`. `posts` содержит строковые messageId/groupedId, результат `detectAd` в `ad`, `reactionBreakdown` как массив `{emoji,count}` или `null`, а также `isViral`, `viralReasons`, `viralPrimaryReason` и `viralMultiplier`. Последний равен `null` без вирусной причины. total учитывает фильтры, absoluteTotal учитывает все посты канала. Поиск реализован Prisma `contains`, без полнотекстового ранжирования. Фильтр `ads` использует сохранённый флаг `Post.isAd`, как и `adShare`; при сборе этот флаг выставляется по `detectAd.isAd || detectAd.isPartner`. Поле `ad` описывает маркеры из текущего текста и может отличаться от сохранённого флага, если текст изменился после классификации.

Запросы страницы `/posts` передают `days` и получают `{posts,total,channels,niches}`. В каждом посте есть источник, сохранённый `isAd`, ER/ERR, `hasImage` и уникальные `@упоминания` по `Mention`. Посты доступны только из активных `UserChannel` текущего пользователя и активных `Channel`; мастер-сессия без `userId` видит все активные каналы. Без `onlyViral` сортировка ER/ERR выполняется в PostgreSQL до пагинации, с пустыми метриками в конце. При `onlyViral=true` поиск сначала классифицирует подходящие посты, затем сортирует и применяет `offset`/`limit`; `total` отражает число вирусных результатов. Некорректные параметры дают 400. Старые запросы `RecentPosts` с `channelId`, `dateFrom`/`dateTo`, `minViews`/`maxViews`, `type` и прежними значениями `sortBy` сохраняют ответ `{posts,total,absoluteTotal}`, но также проходят проверку доступа к каналу.

`GET /api/posts/:id/image` требует доступ к активному каналу публикации и возвращает 404 для недоступного поста или отсутствующего изображения. Ответ с байтами изображения имеет `Cache-Control: private, no-store`.

`GET /api/posts/advertisers?days=7|30&niche=...` требует авторизации. По умолчанию период 30 дней, `niche` необязательна. Ответ `{days,niche,advertisers}` содержит для каждого `@username` число размещений и каналов-доноров, их список, суммарный и средний известный охват, оценку `estimatedSpendUah`, первую и последнюю дату, а также `isTrackedChannel` и `channelId`. Источники ограничены активными каналами текущего пользователя; ID чужого отслеживаемого канала не возвращается. При неизвестных просмотрах охват и бюджет равны `null`.

## AI-отчёты

Все восемь маршрутов используют **POST** и явно проверяют общий гард: UI-сессию или Bearer. Тело JSON. Все используют сохранённый в `SystemSetting` ключ OpenRouter с резервом `OPENROUTER_API_KEY`, стандартный timeout 60 секунд и сохранённую модель с резервом `z-ai/glm-5.3-flash`.

| Путь | Тело | Выборка / основание | Успешный ответ | Тип в AiReport |
| --- | --- | --- | --- | --- |
| `/api/ai/summary` | `{channelId, days?: 7}` | До 50 текстовых постов за период | `{summary: string}` | `summary` |
| `/api/ai/super-report` | `{channelId}` | Последние 50 текстовых постов канала | `{summary: string}` | `super_report` |
| `/api/ai/compare` | `{channelId, days?: 7}` | Целевой канал и «Мой канал», до 50 постов каждого | `{summary: string}` | `compare` |
| `/api/ai/trends` | Не требуется | До 10 текстовых постов на каждый активный канал из списка пользователя за 48 часов; мастер-сессия без `userId` использует все активные каналы | JSON-объект LLM | `trend` |
| `/api/ai/audience` | `{channelId, days?: 7}` | До 20 текстовых постов | `{audience: string}` | `audience` |
| `/api/ai/persona` | `{channelId}` | До 30 последних текстовых постов | `{persona: string}` | `persona` |
| `/api/ai/action-plan` | `{reportId}` | Существующий отчёт | `{summary: string}` | `action_plan` |
| `/api/ai/compare-reports` | `{reportId1, reportId2}` | Два существующих отчёта | `{summary: string}` | `evolution` |

Обозначение `days?: 7` в таблице означает необязательное поле с default 7; пример действительного JSON: `{ "channelId": 1, "days": 7 }`.

Статьи участвуют через `Post.text` наравне с обычными текстовыми публикациями. Дополнительно ограничивается длина контента в промпте: summary и trends — 30 000 символов, super-report — 80 000, compare — по 15 000 на канал. Это лимиты строк в коде, а не лимиты токенов. Audience/persona ограничивают число постов, без отдельного `substring` для всего контента. Восстановление текста не меняет существующие AiReport; новые отчёты запускаются отдельно.

Поля summary/audience/persona содержат **строку**, обычно с JSON от LLM; это не уже распарсенный объект. Ошибки обязательных параметров дают 400; отсутствие контента/канала/отчёта даёт 400 или 404 согласно конкретному обработчику. AbortError даёт 504, сбой соединения с OpenRouter даёт 503 с русским сообщением для повторной попытки, остальные сбои дают 500. Запрос генерации не повторяется автоматически, чтобы не создать второй платный запрос, если первый был обработан до обрыва соединения. `saveAiReport` перехватывает ошибку записи, поэтому 200 не гарантирует наличия отчёта в истории.

### Экспорт

`GET /api/reports/:id/export` возвращает HTML-документ отчёта (`text/html`) после авторизации в middleware. Невалидный ID даёт 400 с текстом, отсутствующий отчёт даёт 404 с текстом, ошибка разбора/рендера даёт 500 с HTML. Это не PDF-endpoint; клиентский PDF-экспорт реализован отдельно.

`DELETE /api/reports/:id` физически удаляет запись `AiReport` после проверки UI-сессии или Bearer. Успех: 200 и `{success:true}`; некорректный ID: 400, отсутствующий отчёт: 404, ошибка БД: 500. После удаления страница отчёта и его HTML-экспорт недоступны. Уже скачанные пользователем файлы не затрагиваются.

## События

- `GET /api/events`: `{events}`, нескрытые события по дате с привязанными постами и каналами; упоминания из явно распознанных дайджестов исключены из ответа, а карточки без других упоминаний скрыты. Совпавшие карточки отображаются одной карточкой со ссылками на все исходные посты. `imageUrl` указывает на сохранённое изображение одного из видимых исходных постов или равен `null`; байты изображения в JSON не включаются. Данные в БД не удаляются. Доступ требует UI-сессию или Bearer через middleware. POST на этом пути не реализован.
- `POST /api/events/scan`: без тела; выбирает до 2000 постов за 14 дней без `eventMentions` и `eventsScannedAt`. Явные дайджесты отбрасывает до OpenRouter Decisions API и отмечает проверенными. Модель `~typesafe/jev-latest` оценивает анонс, пять признаков для ранжирования и отдельные условия: один основной будущий анонс (от 0.5), конкретная дата с условием участия (от 0.5), не отчёт о прошедшем событии (ниже 0.8), не дайджест (ниже 0.8). После успешного Jev отклонённые посты отмечаются проверенными. При ошибке Jev включается прежний фильтр по ключевым словам, не прошедшие его посты остаются для повторной проверки. До 100 отобранных постов передаются в генеративную модель (таймаут 120 секунд) для извлечения деталей; они отмечаются проверенными только после успешного сохранения результата. Event создаётся только с действительным ID исходного поста из выборки. После сохранения совпавшие события транзакционно сливаются с переносом связей и персональных скрытий. Ответ: `{success:true,savedCount,parsedEvents,selectionMode}`, где `selectionMode` равен `jev`, `keyword_fallback` или `no_candidates`. Маршрут явно проверяет UI-сессию или Bearer. Серверный worker может вызвать этот же маршрут по расписанию `EVENTS_SCAN_CRON`; пустая настройка отключает cron.
- `PATCH /api/events/:id/dismiss`: без тела, отмечает событие временем скрытия и возвращает `{success:true}`. Повторный вызов также возвращает успех. Некорректный ID даёт 400, отсутствующее событие даёт 404. Маршрут проверяет UI-сессию или Bearer; для cookie-запроса требуется совпадающий `Origin`. Связи EventMention остаются, поэтому прежние посты не сканируются снова, а новые анонсы могут привязаться к скрытому событию при совпадении даты и названия.
- `GET /api/posts/:id/image`: отдаёт сохранённое изображение поста с исходным `Content-Type`; 400 при некорректном ID, 404 при отсутствии изображения. Доступ требует UI-сессию или Bearer через middleware. Изображение появляется после прохода сборщика по соответствующему посту.

## Настройки

`GET /api/settings` возвращает `{settings}`; при первом чтении создаёт запись `global` с текущей моделью по умолчанию. Поле `aiToken` не возвращается. Вместо него доступны `hasToken`, `tokenPreview` (до четырёх последних символов, для коротких ключей скрыто полностью) и `tokenSource` (`saved`, `environment` или `null`). Доступ требует UI-сессию или Bearer; маршрут также явно проверяет гард.

`POST /api/settings` принимает `{aiProvider,aiModel,aiToken,clearToken,digestEnabled,digestHour}` и возвращает `{success:true,settings}` без полного токена. Оба поля дайджеста необязательны: `digestEnabled` должен быть boolean, `digestHour` целым числом от 0 до 23 (UTC); неверные значения дают 400. GET и POST возвращают также `lastDigestAt` (время последней успешной отправки или `null`). Поддерживается `aiProvider: "openrouter"`; пустая модель выбирает `z-ai/glm-5.3-flash`. Пропущенный, пустой или маскированный `aiToken` не меняет сохранённый ключ. Для явного удаления сохранённого ключа передайте `clearToken: true`; если задан `OPENROUTER_API_KEY`, он продолжит работать как резерв. Успешная запись сбрасывает кэш конфигурации текущего web-процесса. Маршрут явно проверяет UI-сессию или Bearer; запись доступна только ADMIN.

Дайджест использует глобальные активные каналы (`Channel.isActive`) и глобальный `Channel.isMine`. Он включает число каналов, известную суммарную аудиторию, метрики «Моего канала», по три лидера роста и падения за 24 часа, число сохранённых антифрод-сигналов с `detectedAt` за последние 24 часа и текущее число каналов с `consecutiveErrors > 0`. Worker использует `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`; при ошибке доставки отметка `lastDigestAt` возвращается к прежнему значению для повторной попытки в выбранный час.

## Правила уведомлений

Все методы `/api/alerts` проверяют UI-сессию или Bearer в обработчике. В Web UI правила находятся на странице `/settings`.

| Метод | Вход | Ответ |
| --- | --- | --- |
| `GET /api/alerts` | Нет тела | `{rules,channels,metrics,deliveryConfigured}`; флаг показывает наличие конфигурации Bot API без выдачи токена |
| `POST /api/alerts` | `{channelId:null,metric:"followers",operator:"gt",threshold:1000}` или `{channelId:null,metric:"keyword",keywordQuery:"биткоин, тон"}` | 201 и `{rule}`; 400 для неверного типа/порога/запроса, 404 для отсутствующего канала, 409 для уже существующего сочетания параметров |
| `PATCH /api/alerts` | `{id,enabled}` | 200 и `{rule}`; 404, если правило удалено |
| `DELETE /api/alerts` | `{id}` | 200 и `{success:true}`; 404, если правило не найдено |

`channelId:null` применяет правило отдельно к каждому активному каналу. Для пользовательского правила нужна активная связь `UserChannel` владельца с каналом; правило без `userId` работает по всем активным каналам. Cooldown 24 часа для числовых метрик хранится для пары «правило и канал» в `AlertRuleFire`, а для `metric:"keyword"` срабатывание фиксируется отдельно на каждый совпавший пост в `AlertRulePostFire`; `AlertRule.lastFiredAt` показывает последнюю успешную отправку по любому каналу. Поддерживаются `followers`, `delta24h`, `delta7d`, `er7d`, `err7d`, `vr7d`, `avgViews7d`, `posts7d`, `contentScore` и `keyword`. Для `keyword` поле `keywordQuery` обязательно (до 100 символов, список фраз через запятую, регистронезависимый поиск по новым постам за последние 24 часа; уведомление включает сниппет до 200 символов и ссылку на пост). Дельты измеряются числом подписчиков со знаком, ER/ERR/VR в процентах. `gt` и `lt` используют строгое сравнение; отсутствующая метрика пропускается. При неудачной доставке резервирование пары освобождается. Сообщение содержит тип правила и `@username` канала, если он известен.

## Сбор, health и кэш

### `POST /api/collect/run`

Явная проверка UI-сессии или Bearer, тело не требуется. Web передаёт задачу во внутренний API worker, ждёт завершения цикла и очищает оба кэша. Ответ:

```json
{
  "success": true,
  "message": "Цикл сбора успешно завершен",
  "result": {
    "totalChannels": 2,
    "successCount": 1,
    "errorCount": 1,
    "totalPosts": 20,
    "totalSnapshots": 1,
    "durationMs": 5000
  }
}
```

Это иллюстрация формы, не результат реального сбора. `success: true` не гарантирует успех каждого канала; проверяйте счётчики и SyncJob. Если сбор уже выполняется или ожидает в очереди, маршрут возвращает 409 `{ "error": "Сбор уже выполняется" }`. При недоступном worker возвращает 503. Активный SyncJob защищён транзакционной блокировкой PostgreSQL.

### `GET /api/health`

Проверяет соединение с БД через `SELECT 1`, читает последний SyncJob по startedAt и самый ранний активный канал, без Bearer:

| Условие | Статус |
| --- | --- |
| Нет активных каналов и нет зависшего SyncJob | 200, `{status:"idle"}` |
| SyncJob ещё нет, активный канал создан недавно или web запущен недавно | 200, `{status:"initializing"}` |
| SyncJob ещё нет, активные каналы есть, прошло больше HEALTH_STALE_THRESHOLD_MINUTES (720) с запуска web и создания самого раннего активного канала | 503, `sync job stale` |
| Нет endedAt и прошло больше HEALTH_STUCK_THRESHOLD_MINUTES (120) | 503, `sync job stuck` |
| После endedAt прошло больше HEALTH_STALE_THRESHOLD_MINUTES (720), есть активные каналы | 503, `sync job stale` |
| БД недоступна | 503, `database unavailable` |
| Остальное | 200, `{status:"ok",lastSyncStatus,lastSyncEndedAt,channelsSucceeded,channelsFailed}` |

Свежий FAILED/PARTIAL также может дать HTTP 200: handler проверяет давность, а не успешность сбора. Это не проверка lastCollectedAt каждого канала. Окно `initializing` отсчитывается заново при перезапуске web.

### `GET /api/ops/status` и `POST /api/ops/status`

Оба метода требуют сессию или Bearer с ролью `ADMIN`; для `USER` возвращают 403. GET возвращает `{latestJob,jobs,summary,problemChannels}`. `jobs` содержит до 20 последних `SyncJob` по `startedAt` убыванию. `summary.lastSuccessfulAt` берётся из последнего `COMPLETED`, `successRate7dPercent` равен доле `COMPLETED` среди `COMPLETED`/`PARTIAL`/`FAILED` за последние 7 дней; `RUNNING` не входит в знаменатель, отсутствие завершённых запусков даёт `null`. `disabledWithErrors` считает отключённые каналы, у которых есть счётчик ошибок или `lastError`. `problemChannels` включает и активные каналы с ошибками.

POST принимает `{ "action": "reset-channel-errors", "channelId": 123 }`, где `channelId` является положительным целым числом. Для существующего проблемного канала он сбрасывает `consecutiveErrors` и `lastError`, включает `Channel.isActive`, активирует существующий `UserChannel` администратора и очищает кэши метрик и времени публикации. Новая пользовательская подписка не создаётся. Ответ 200: `{success:true,channel}`; неверное тело даёт 400, отсутствующий канал 404, канал без ошибок 409. Восстановление действует со следующего цикла сбора. Если канал был выключен вручную и у него осталась ошибка, явное действие администратора тоже включит его.

### `POST /api/internal/invalidate-cache`

Явная проверка Bearer, пустое тело. Очищает `metricsCache` и `bestTimeCache` **текущего web-процесса**. Ответ: `{ "success": true }`, HTTP 200. Worker вызывает его после основного цикла, если заданы WEB_INTERNAL_URL и COLLECT_API_TOKEN.
