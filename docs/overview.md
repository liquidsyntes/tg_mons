# Обзор TgMon

TgMon собирает данные Telegram через MTProto, хранит их в PostgreSQL и помогает сравнивать каналы с собственным. В приложении реализована **многопользовательская система с регистрацией по инвайт-кодам (Вариант А)**: пул собираемых каналов и ключ OpenRouter общие, но каждый пользователь работает со своим списком каналов (`UserChannel`), своими флагами «Мой канал» и «Избранное», своими AI-отчётами, правилами уведомлений и скрытыми событиями.

Описание пользовательских функций сверено с реализацией 20 октября 2026 года. Начало работы: [README](../README.md); точные расчёты: [справочник формул](analytics-formulas.md).

## Пользовательские сценарии

| Страница | Возможности |
| --- | --- |
| `/login` | Вход по логину/паролю, регистрация по инвайт-коду (`/login?invite=TGMON-...`) и резервный вход администратора по мастер-ключу (`COLLECT_API_TOKEN`) |
| `/` | Добавление каналов в личный список, ручной сбор, «Мой канал», избранное, сравнительная таблица, общие KPI, лидеры роста/падения, лучшее время публикации, радар трендов |
| `/channel/:id` | Подписчики, активность, heatmap, ER/ERR/VR, Content Score, сигналы риска, поиск публикаций, Content LTV, цитирование, рекламный охват, AI-отчёты, отключение и удаление из своего списка |
| `/posts` | Глобальный поиск публикаций в активных каналах пользователя, фильтр рекламных постов (Ad Spy), ниши, период, сортировка и сохранённые изображения |
| `/compare` | Сравнение двух каналов по периодам 24ч/7д/30д |
| `/reports`, `/reports/:id` | Персональная история сохранённых AI-отчётов, сравнение отчётов, план действий, HTML-экспорт и безвозвратное удаление отчёта из архива |
| `/events` | Просмотр событий из отслеживаемых пользователем каналов с доступными изображениями из исходных постов, ссылки на посты, персональное скрытие карточки и запуск сканирования анонсов |
| `/settings` | Управление инвайт-кодами и общим ключом/моделью OpenRouter, мониторинг запусков и восстановление каналов (только для `ADMIN`), настройка персональных правил Telegram-уведомлений (`AlertRule`) |

В таблице закреплена колонка Channel, сортировка доступна кнопками. Для групп вместо ERR показывается CR за 7 дней. Нулевые метрики отображаются как ноль. При отсутствии постов пустые ячейки используют голубой индикатор за 24 часа и розовый за 7 дней с подсказкой. Дельты показывают покрытие истории, если оно отличается от номинального периода больше чем на день.

На странице канала блок «Сетка каналов» можно свернуть и развернуть. Сравнение графика участников с «Моим каналом» при открытии страницы выключено и включается отдельным переключателем.

Радар трендов свёрнут по умолчанию. Раскрытие показывает последний сохранённый отчёт, а кнопка обновления запускает новую генерацию (анализирует посты активных каналов из избранного (Watchlist, `isFavorite: true`) и «Моего канала» (`isMine: true`) за последние 48 часов). KPI ERR усредняет известные `err7d` только активных каналов, исключая группы; при отсутствии данных показывает `н/д`. Остальные KPI и временные ряды дашборда также исключают отключённые каналы.

## Какие данные собираются

- Аудитория, заголовок канала, обычные тексты и тексты статей Telegram, просмотры, реакции, комментарии и пересылки.
- Упоминания `@username`, ссылки на Telegram и источники пересылок, найденные в собранных постах. Это ограниченный граф наблюдаемых каналов, а не поиск по всему Telegram.
- При первом сборе — до 1000 сообщений с отсечением публикаций старше 30 дней; далее — до 200 последних сообщений за цикл. Медиаальбомы объединяются по `groupedId`.
- Отдельное фото или изображение-документ Telegram до 1 МБ сохраняется для поста; медиа внутри статей и видео не сохраняются.
- `subscribersAtPublish` сохраняется при первом обнаружении поста и не обновляется обычным upsert. Для исторических постов это может быть аудитория во время сбора, а не публикации.
- Тип контента сообщений классифицируется при сборе (`Post.contentType`: `text`, `photo`, `video`, `poll`, `link`), что позволяет сравнивать вовлечённость по форматам.
- Снимки просмотров свежих постов для Content LTV и отдельные контрольные точки рекламного охвата.

Обычный сбор запускается по cron, по желанию при старте worker и вручную из web. В основном цикле worker материализует дневные метрики и записывает сработавшие антифрод-сигналы для каждого обработанного канала; после завершения цикла запрашивает сброс web-кэша. [Полный поток](architecture.md).

Администратор видит на `/settings` последние 20 циклов `SyncJob`, долю полностью успешных завершённых циклов за 7 дней и каналы с ошибками сбора. Краткие причины ошибок каналов сохраняются в новых частичных циклах; старые записи `PARTIAL` могут не содержать `errorSummary`. Кнопка восстановления сбрасывает ошибки и включает сбор канала со следующего цикла. Отключённые каналы с ошибками не всегда можно достоверно отличить от выключенных вручную.

## Чтение статей

Статьи Telegram поступают в отдельном поле `richMessage`. Сборщик на teleproto догружает частичные статьи, переводит их содержимое в обычный текст и сохраняет в `Post.text`. Карточка показывает сокращённый текст, нажатие открывает окно с полным сохранённым текстом и прокруткой. Переход в Telegram остаётся дополнительной кнопкой, а не условием чтения текста статьи.

Сохраняются текстовые заголовки, абзацы, списки, цитаты, таблицы и подписи. Встроенные изображения, OCR и исходное оформление не поддерживаются. «Текст недоступен» может означать медиа без подписи, неподдерживаемый формат или прежний пропуск сбора. Причина отдельным полем в БД не хранится.

Уже пустые записи можно восстановить [утилитой](../scripts/README.md#восстановление-текста-статей). Поиск, классификация рекламы и новые AI-отчёты получают обновлённый текст; старые отчёты автоматически не меняются.

## Аналитика

ER учитывает просмотры и взаимодействия относительно `subscribersAtPublish`. ERR учитывает реакции, комментарии и пересылки относительно просмотров. CR — средние комментарии на пост относительно аудитории группы. VR — средние просмотры относительно аудитории.

Детектор «тишины» канала (`detectSilencePeriods`) отслеживает длительные паузы между публикациями (> 7 дней по умолчанию) за последние 90 дней и определяет текущий статус активности канала: `активен` (последний пост < 3 дней назад), `замедлился` (3–7 дней) или `молчит` (> 7 дней или отсутствие постов). Статус визуализируется в `StatusBadge` и подсвечивает угасающие каналы в `WatchlistWidget` (Избранное).

EP нормализует рост, медианный охват и вовлечённость внутри `niche`. Content Score — отдельная сумма баллов за вовлечённость, частоту, рост, разнообразие взаимодействий и долю рекламы; z-нормализации в нём нет.

`Ad Load` использует сохранённый флаг `Post.isAd`, включающий рекламные и партнёрские публикации. Оценка стоимости рекламы опирается на до 30 последних таких постов и фиксированные CPM из `src/lib/pricing.ts`; это расчёт приложения, а не текущая рыночная котировка.

На странице канала виджет «Эффективность размещений» показывает входящие упоминания и исходящие рекламные посты с другими доступными отслеживаемыми каналами. Он сопоставляет снимки аудитории до публикации и спустя 24/48 часов, выводит оценочные цену поста, CPF и конверсию из текущих просмотров. Пересекающиеся кампании помечаются отдельно; показанный прирост может включать органические подписки и другие источники.

Антифрод проверяет гладкость роста, необъяснимые скачки, отношение просмотров к аудитории и равномерность ERR. Каждый сработавший тип даёт 25 баллов. Сохранённые сигналы за 30 дней могут удерживать балл после исчезновения исходной аномалии. Отсутствие сигналов при недостатке данных не подтверждает качество аудитории.

## Демография

Отдельное недельное задание собирает языковой граф только активного «Моего канала» типа `channel`. Нужны `canViewStats` и доступный `statsDc`. Недоступная или повреждённая статистика пропускается без пустого снимка и без увеличения `consecutiveErrors`.

Языковые доли берутся по последней общей точке графика. Вместе со статистикой собирается доля подписчиков с включёнными уведомлениями (`notificationsEnabledPercent`, показатель лояльности аудитории). `countries` всегда `null`, `geographyStatus` — `unsupported`; язык не преобразуется в страну. Виджет показывает дату снимка, процент включённых уведомлений и отмечает данные старше недели. AI-отчёт об аудитории анализирует тексты и не заменяет эту статистику Telegram.

## AI и события

Восемь POST-маршрутов используют общий OpenRouter-клиент: summary, super-report, compare, trends, audience, persona, action-plan, compare-reports. Модель в коде: `z-ai/glm-5.3-flash`, стандартный таймаут: 60 секунд. Вывод сохраняется в `AiReport`; ошибка сохранения логируется и не обязательно делает генерацию неуспешной. В архиве отчёт можно скачать как HTML или безвозвратно удалить после подтверждения. Удаление убирает запись из БД, страницу отчёта и доступ к его экспорту; ранее скачанный файл остаётся у пользователя.

Сканер событий читает до 2000 текстовых постов за 14 дней без связей с событиями. Jev через OpenRouter проверяет первые 4000 символов каждого непустого текста на признаки конкретного анонса, даты, времени, приглашения, билетов и регистрации, без предварительного фильтра по словам. Посты с оценкой основного признака ниже 0.2 исключаются. Остальные упорядочиваются по внутреннему рейтингу: 60% веса у признака анонса, 40% у пяти дополнительных признаков. Рейтинг не является калиброванной вероятностью, а порог ещё не проверен на размеченных постах TgMon. При ошибке Jev включается прежний фильтр по ключевым словам, о чём сообщает интерфейс. До 100 отобранных постов передаются в генеративную модель с таймаутом 120 секунд для извлечения дат и других деталей. Совпадающие даты и похожие названия объединяются. Автоматического расписания этого сканера в worker нет.

Явные дайджесты и подборки нескольких разных мероприятий отбрасываются до вызова Jev. Для подборок без метки Jev отдельно оценивает, описывает ли пост несколько самостоятельных событий; при оценке от 0.8 пост не передаётся генеративной модели. Та также получает правило не извлекать события из дайджестов. При чтении «Афиши» упоминания из явно распознанных дайджестов скрываются, а карточки без других упоминаний не показываются. Записи в БД остаются: это не очистка данных. Старые дайджесты без явных признаков могут остаться видимыми, так как оценки Jev для них не сохранялись.

События с одинаковой датой сопоставляются по названию. При разных названиях дополнительно требуются одинаковое время, общий организатор и несколько совпадающих значимых слов названия. Новые упоминания связываются с найденным событием; ранее созданные совпавшие записи при чтении показываются одной карточкой с объединёнными ссылками на посты. Записи БД при этом не сливаются.

Дополнительно Jev требует, чтобы пост был в первую очередь анонсом одного будущего события (оценка от 0.5) и содержал конкретную дату вместе хотя бы с одним условием участия: время, место, онлайн-площадку, билет, регистрацию или контакт (оценка от 0.5). Отчёт о прошедшем событии с подборкой будущих дат отсекается при оценке от 0.8. Генеративная модель получает те же ограничения и больше не должна угадывать неточную дату. Событие сохраняется только при наличии хотя бы одного действительного исходного поста из отобранной выборки. Эти пороги пока проверены на отдельных примерах, но не откалиброваны на размеченном наборе.

Кнопка «Убрать» скрывает отдельное событие после подтверждения. Событие и связи с постами остаются в БД: прежние посты не возвращаются в выборку сканера, а новый анонс с той же датой и близким названием может привязаться к скрытой записи. Если модель сильно изменит дату или название, возможно появление новой карточки; более надёжное сопоставление мероприятий требует отдельной доработки.

При сборе постов отдельное фото Telegram или изображение-документ до 1 МБ сохраняется в `PostImage`. Для альбома сохраняется первое доступное изображение связанного поста. «Афиша» показывает изображение из одного из видимых упоминаний, включая объединённые карточки; при его отсутствии остаётся заглушка. Ранее собранные посты получат изображение только при повторном проходе сборщика по этим сообщениям. Медиа внутри Telegram-статей и видео пока не сохраняются.

Страница `/posts` ищет публикации по тексту во всех активных каналах из личного списка. Мастер-сессия администратора видит все активные каналы. Режим Ad Spy выбирает сохранённый `Post.isAd`, который включает рекламные и партнёрские публикации. ER и ERR отдельного поста рассчитываются по тем же формулам, что и аналитика канала; при отсутствии знаменателя отображается `н/д`. Изображения доступны только пользователям, которым доступен исходный канал.

## Границы текущей реализации

- Вход Web UI поддерживает пользовательские аккаунты (`User`, роли `ADMIN` и `USER`) с регистрацией по инвайтам (`InviteCode`), а также резервный вход по `COLLECT_API_TOKEN`. Сессия хранится в подписанной `HttpOnly`-cookie (`v2` или `v1`) с проверкой `Origin` для мутаций; `worker` использует `Bearer`. `/api/settings` и `/api/invites` доступны только роли `ADMIN`.
- MTProto-сессии разделены между средами: серверный воркер использует `TG_SESSION` (`TgMon Server Worker`), локальный воркер (`worker:local`) — строго отдельную `TG_SESSION_LOCAL` (`TgMon Local Dev`) без фонового cron, что предотвращает `AuthKeyDuplicated`.
- Счётчики и временные окна отличаются между сырым и материализованным путями; они описаны в [формулах](analytics-formulas.md).
- Запоздалый запуск сбора рекламного охвата записывает текущие просмотры во все пропущенные контрольные точки. Он не восстанавливает реальные исторические просмотры.
- Пользовательские AlertRule на `/settings` проверяются worker после расчёта метрик. Cooldown составляет 24 часа для каждой пары «правило и канал». Глобальное правило пользователя применяется только к его активным `UserChannel`; системное правило без `userId` применяется ко всем активным каналам. Автоотключение канала также отправляет уведомление. Администратор управляет ежедневным Telegram-дайджестом на `/settings`: выбирает час UTC, включает отправку и видит время последней успешной доставки. Worker проверяет расписание каждые пять минут, отправляет сводку по активным каналам через Bot API и не отправляет её повторно в те же UTC-сутки. В локальном режиме и при отключённом cron фоновый дайджест не отправляется.
- `MY_CHANNEL_USERNAME` из `.env.example` не используется кодом; назначение выполняется через UI/API.
