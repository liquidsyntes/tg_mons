# Ревью реализации таймаутов Telegram (GramJS)

Данный документ содержит ответы на вопросы аудита безопасности реализации `withTimeout` для сетевых запросов к Telegram.

## 1. Очистка таймеров
Реализация корректно очищает `setTimeout` с помощью `clearTimeout(timer)` внутри блоков `.then()` и `.catch()` исходного промиса. Если запрос завершается успешно или возвращает ошибку до истечения таймаута, таймер уничтожается, предотвращая утечки памяти.

## 2. Необработанные Rejections (UnhandledPromiseRejection)
В текущей реализации:
```typescript
promiseFn()
  .then(...)
  .catch((err) => {
    clearTimeout(timer);
    reject(err);
  });
```
Если таймаут срабатывает первым, внешний `Promise` реджектится с ошибкой `TelegramTimeoutError`. Исходный запрос продолжает выполняться в фоне. Если он впоследствии (например, через 5 минут) завершится ошибкой, сработает блок `.catch`, который вызовет `reject(err)`. 
Так как внешний промис уже завершен, повторный вызов `reject` будет безопасно проигнорирован (no-op по спецификации Promises/A+). Поскольку к исходному промису прикреплен обработчик `.catch`, ошибки `UnhandledPromiseRejectionWarning` на уровне процесса Node.js не возникнет.

## 3. Отмена фактического запроса
Текущий механизм работает по принципу логического отсечения ожидания (похоже на `Promise.race`). Он **не отменяет** фактический сетевой запрос внутри библиотеки GramJS. Запрос продолжает "висеть" в памяти и на уровне сокета, пока библиотека сама его не оборвет.

## 4. Поддержка AbortSignal в GramJS
Согласно документации библиотеки GramJS (на текущих версиях), методы `client.invoke`, `client.getMessages` и `client.getEntity` **не поддерживают** стандартный веб-механизм `AbortSignal` или токены отмены. В GramJS запросы мультиплексируются поверх единого TCP-соединения (MTProto). Единственный гарантированный способ принудительно прервать "зависший" запрос на уровне сокета — это вызвать `client.disconnect()`, что приведет к разрыву соединения целиком.

## 5. Оценка риска «фонового зависшего запроса»
Поскольку GramJS не умеет точечно отменять запросы, зависший промис останется в памяти до тех пор, пока TCP-сокет не закроется по системному keep-alive таймауту. 
В нашей последовательной модели сбора это несет **низкий риск**, так как мы переходим к следующему каналу и используем тот же клиент.
Если сокет реально мертв, следующие каналы тоже упадут по таймауту. 
**Самый безопасный вариант поведения (рекомендация):**
Оставить текущую логику таймаута как есть, но при получении `TelegramTimeoutError` рекомендуется принудительно переподключать клиент (вызывать `client.disconnect()` и затем заново инициировать соединение перед следующим каналом), чтобы сбросить "мертвый" сокет и очистить очередь MTProto-запросов.

## 6. Исключение бесконечных ретраев FLOOD_WAIT
В функции `withRateLimitAndRetry` проверка на `FLOOD_WAIT` осуществляется поиском строки в `err.errorMessage` или чтением свойства `err.seconds`. 
Класс `TelegramTimeoutError` не имеет этих свойств и его свойство `message` не содержит "FLOOD_WAIT_". Соответственно, обертка не будет пытаться ретраить таймаут и сразу выбросит ошибку наверх, перейдя к следующему каналу.

## 7. Ревью тестов (timeout.test.ts)
Написанные тесты покрывают:
- Успешное выполнение до таймаута.
- Успешный проброс внутренней ошибки до таймаута.
- Выброс `TelegramTimeoutError`, если промис "зависает".
- Проверку дефолтного значения 30000ms.
Тесты корректно изолированы и не оставляют висящих таймеров в event loop благодаря очистке.

## Итог
**Текущую реализацию можно принимать.** Она безопасна, предотвращает "вечное" зависание цикла сбора и не вызывает утечек `UnhandledPromiseRejection`. 

**Предложенный минимальный план на будущее (без изменений сейчас):**
В файле `src/worker/collector.ts` в главной функции цикла `runCollectCycle()` в блоке `catch`:
```typescript
if (err instanceof TelegramTimeoutError) {
  // Принудительный сброс клиента, так как сокет, вероятно, мертв
  await client.disconnect();
  client = await getTelegramClient(); // Пересоздаем клиент для следующих каналов
}
```
