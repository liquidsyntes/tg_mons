# Памятка по TgMon

Сверено 20 октября 2026 года. Это краткий указатель на текущую реализацию, а не отдельное ТЗ. Правила работы: [AGENTS.md](AGENTS.md), [GEMINI.md](GEMINI.md), [рабочий процесс](docs/codex-workflow.md).

## Основные ориентиры

- Основной checkout — `C:\TgMon` / `/mnt/c/TgMon`; работать в нём с учётом незакоммиченных изменений.
- Web — Next.js App Router, React, TypeScript и Tailwind; компоненты собственные, зависимости shadcn/ui нет. Радиусы карточек и графиков — 3 px; аватары и индикаторы могут быть круглыми.
- БД — PostgreSQL с Prisma. Текущие модели и ограничения определяются [схемой](prisma/schema.prisma), включая многопользовательские модели (`User`, `InviteCode`, `UserChannel`, `UserDismissedEvent`).
- Сборщик — teleproto (`telegram` в импортах, npm alias в package.json). Серверная MTProto-сессия хранится в `TG_SESSION` (`TgMon Server Worker`), локальная — строго в `TG_SESSION_LOCAL` (`TgMon Local Dev`, создаётся через `npm run auth:local:qr` или `npm run auth:local`). Bot API используется только для опциональных уведомлений.
- Локальный запуск — нативно через `bash dev-web.sh` (`npm run dev:local`, без фонового cron в локальном воркере). Боевой сервер OVH (`/opt/tgmon`) — полный Docker Compose (`postgres`, `web`, `worker`), обновляется через `bash update.sh`.

## Поведение, которое важно сохранять

1. Первый сбор: до 1000 сообщений за последние 30 дней; обычный цикл: до 200 последних сообщений без `min_id`, с обновлением счётчиков существующих записей.
2. Статьи: `richMessage` → догрузка при `part=true` → обычный текст в `Post.text`. Ошибка догрузки не затирает полный текст и не останавливает сбор остальных сообщений.
3. Retry — пауза перед вызовом и повтор при FLOOD_WAIT с указанным Telegram временем и jitter; распределённого лимитера и экспоненциального backoff в текущем коде нет.
4. Ошибки каналов изолируются; дополнительные Telegram-статистики не должны ломать основной сбор. Web также выполняет сбор при добавлении канала и ручном запросе.
5. Дневные агрегаты хранятся в БД. Их календарные UTC-окна отличаются от скользящих окон сырых постов; формулы нельзя выводить из подписей UI.
6. «Мой канал» назначается через UI/API, прежний флаг снимается транзакцией. Канал с этим флагом может отсутствовать; `MY_CHANNEL_USERNAME` не используется кодом.
7. Отключение сохраняет историю; постоянное удаление канала удаляет связанные данные по каскадам.
8. Web UI поддерживает многопользовательские аккаунты (`User`, роли `ADMIN` и `USER`) с регистрацией по инвайтам (`InviteCode`), персональными подписками на каналы (`UserChannel`) и резервным входом по `COLLECT_API_TOKEN` (подписанная `HttpOnly`-cookie `v2`/`v1`). Middleware проверяет cookie и `Origin` для изменений; `worker` использует `Bearer`. Ключ OpenRouter общий, управляется администратором.
9. Сборщик сохраняет одно изображение поста до 1 МБ, а «Афиша» показывает его при наличии. Архив AI-отчётов физически удаляет выбранную запись только после подтверждения пользователя.
