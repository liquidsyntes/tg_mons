## Цель продукта

Дашборд, который за 10 секунд отвечает на три вопроса:
1. Кто из отслеживаемых каналов растёт быстрее «моего канала»?
2. Кто сколько публикует?
3. Какова текущая позиция «моего канала» на фоне конкурентов?

«Мой канал» — ровно один канал с `isMine = true`. Задаётся в конфигурации, переназначается через UI/API. При назначении нового «моего канала» снимать флаг с предыдущего в одной транзакции.

## Стек (фиксированный)

| Уровень | Технологии |
| :--- | :--- |
| Frontend + API | Next.js (App Router), TypeScript, Tailwind CSS, shadcn/ui, Recharts |
| База данных | PostgreSQL + Prisma ORM |
| Коллектор | Node.js worker + gramjs (MTProto). Альтернатива: Python + Telethon — только с обоснованием |
| Инфраструктура | Docker Compose (`web`, `worker`, `db`), конфигурация через `.env` |

## База данных

Схема Prisma — точно по ТЗ (модели `Channel`, `Snapshot`, `Post` с указанными полями, индексами и `@@unique([channelId, messageId])` для постов). Менять только с записью причины в README.

Правила работы с данными:
- Все даты — в UTC. Периоды «24ч / 7д / 30д» считаются как `now() - interval`, а не календарные сутки.
- `members_at(period)` — ближайший снапшот не позже границы периода: `WHERE collected_at <= now() - interval ORDER BY collected_at DESC LIMIT 1`.
- Если истории на период нет (канал добавлен недавно) — метрика `null`, в UI отображается `н/д`, а не `0`.
- Удаление канала из мониторинга — мягкое: история (снапшоты, посты) сохраняется. Каскадное удаление в схеме — для физического удаления записи, не для «отключения мониторинга».

## Worker (MTProto-сборщик)

Отдельный фоновый процесс, не блокирующий веб-сервер. Запуск по `node-cron` с расписанием из `COLLECT_CRON`.

Обязательные требования:
- **Rate limit:** глобально ~1 запрос/сек, последовательный обход каналов, никакого параллельного спама.
- **FLOOD_WAIT_*:** перехват ошибки, ожидание указанного времени + экспоненциальный backoff с джиттером, затем повтор.
- **Инкрементальный сбор постов:** `messages.getHistory` строго с `min_id = lastMessageId` канала; после успешного цикла обновлять `lastMessageId` на максимальный собранный. Дедупликация — upsert по `(channel_id, message_id)`.
- **Первичный бэкфилл:** при добавлении канала — сбор истории глубиной 30 дней.
- **Изоляция ошибок:** сбой по одному каналу (бан, переименование, недоступность) → записать текст в `lastError`, обновить статус, продолжить обход остальных. Воркер не падает.
- **Метаданные** (название, аватар, описание) — обновлять раз в сутки, не каждый цикл.
- **Логирование:** каждый цикл — канал, длительность, статус, число собранных постов/снапшотов.
- Приватные каналы — только если аккаунт сборщика уже состоит в них (инвайт-ссылки).

Периодичность: участники (`channels.getFullChannel` → `participants_count`) и посты — каждый час; метаданные — раз в сутки.

## API (Route Handlers)

| Метод | Эндпоинт | Назначение |
| :--- | :--- | :--- |
| `GET` | `/api/channels` | Список каналов с последними метриками |
| `POST` | `/api/channels` | Добавить канал: принимает `@username`, `t.me/...` или инвайт-ссылку; resolve → `tgId`; запуск бэкфилла |
| `PATCH` | `/api/channels/:id` | Переключить `isActive`, назначить «моим каналом» (`isMine`, транзакционно) |
| `DELETE` | `/api/channels/:id` | Отключить от мониторинга (история сохраняется) |
| `GET` | `/api/stats/overview` | Сводка для главной: каналы, дельты, сравнение с «моим» |
| `GET` | `/api/stats/channel/:id?period=7d` | Таймсерии для графиков (подписчики, посты по дням) |
| `POST` | `/api/collect/run` | Ручной триггер цикла сбора; защита Bearer-токеном (`COLLECT_API_TOKEN`) |

Вычисляемые метрики (на лету из БД, не хранить):
- Δ участников за 24ч/7д/30д: абсолютное значение + процент.
- Посты за 24ч/7д/30д: `COUNT` по `published_at >= now() - interval`.
- Средняя частота: постов в день за последние 30 дней.
- Сравнение с «моим каналом»: доля аудитории (%), разница темпов роста (% за 7д), разница активности (постов за 7д).

## Frontend

Дизайн-система:
- Тёмная тема по умолчанию, минимализм, воздух, без лишних рамок/теней/плашек.
- 1 акцентный цвет бренда + семантические цвета дельт (зелёный — рост, красный — спад).
- Числовые колонки — `tabular-nums`.

Страницы:
1. **Главная (Overview):** крупная карточка «Мой канал» (подписчики, Δ 24ч/7д/30д, посты 24ч/7д/30д); сравнительная таблица (название, username, участники, Δ с цветом и стрелками, посты, колонка «% от моего», сортировка по любому столбцу). «Мой канал» — всегда первая подсвеченная строка. На мобильных таблица перестраивается в карточки.
2. **Детальная страница канала:** Line Chart участников за 30 дней, Bar Chart постов по дням, переключатель периодов (24ч/7д/30д), тумблер наложения кривой «моего канала».

Состояния UI: Loading — скелетоны (не спиннеры); Empty — приветствие с призывом добавить первый канал; Error — информативный текст ошибки сбора. Статус сбора по каналу: `успешно` / `ошибка` / `давно не обновлялся` (по `lastCollectedAt` и `lastError`).

## Известные риски

- Приватные каналы/группы: сбор только если аккаунт сборщика вступил в чат заранее.
- Flood Wait: строгий rate limit (~1 rps) и корректные паузы обязательны, иначе заморозка сессии.
- Дискретность метрик: точность динамики подписчиков ограничена частотой крона — это норма, не «чинить».
